# 策划 Bug 同步检查

## 文档来源

外部 Obsidian 目录：
`C:\Users\jinji\Desktop\文档\MyNote\游戏开发项目\卡牌地下城\未解决问题`

## 执行流程

1. **读取最新日期的未解决问题文档**：
   列出目录下所有 `.md` 文件，按文件名日期排序，读取最新的一份。

2. **提取未解决 Bug 列表**：
   扫描文档中所有 `- [ ]` 条目，即为当前待解决的策划汇报 Bug。

3. **分析Bug规模**：
   如果Bug汇报较多，考虑安排子代理，拆分任务，或者分批处理。

4. **逐个代码核对+修复**：
   针对每个未解决 Bug，在代码库中定位相关模块（词条、卡牌、怪物、商店、事件、计策、关卡、遗物等），核对权威设计文档（路径：：C:\Users\jinji\Desktop\文档\MyNote\游戏开发项目\卡牌地下城\第二版设计），判断该 Bug 是否已在最新代码中修复，是否对得上设计，若没有则进行修复，若已修复则进入第五步。

5. **标记已解决条目**：
   若确认已修复，将对应 `- [ ]` 改为 `- [x]`，并在该行末尾紧跟标注 `（AI自动生成，待验证）`。若未完成所有Bug的核对和修复，则回到第四步继续处理剩余条目。
   > 注意：标注必须紧贴条目原文之后，不要换行。

6. **保持文档结构**：
   只修改已确认修复的条目状态，不增删其他内容，不改文件其余格式。

## 判断修复的参考方法

- 查看相关数据定义（`js/data/`、`js/systems/` 等），确认逻辑已按 Bug 描述修正。
- 查看最近的 Git 提交记录，确认有对应修复。
- 若代码逻辑已明显符合设计意图，即可判定为已修复。

## 禁止项

- 不可将未确认的 Bug 擅自标记为已解决。
- 不可修改文档中的 `- [x]` 条目（除非需要补充标注）。
- 不可改变文档的章节结构和标题。
