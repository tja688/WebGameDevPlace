## 现状判断

当前代码已经能运行基础关卡、点击战斗、补牌、顺时针旋转、道具牌格、遗物和少量玩家技能。

但复杂技能模块尚未成体系：

- `SkillManager` 只保存玩家技能和静态属性加成，没有统一触发器。
- 怪物技能分散硬编码在 `BattleResolver.resolveBattle()`、`GameScene._placeCardOnGrid()` 等位置。
- `GridManager.rotateGrid()` 只执行视觉移动和更新 `slotContents`，没有输出“哪些卡从哪里移动到哪里”的移动事件。
- 设计文档要求的统一结算链中，`onMove / 移动到格X / 每移动N次 / removeCard / killMonster` 没有完整事件管线。
- `removeCard` 和 `killMonster` 的语义还未拆开。当前多处直接 `destroy()`，容易漏触发金币、遗物、怪物被移除技能。
- `洗入战斗卡组` 当前代码多用 `unshift()` 放到牌堆顶，但这里的洗入指的是随机混合。
- 当前 `TestData.js` 中只有少量怪物技能被挂载，且与 `07-数据/怪物卡数据.md` 存在明显差距。

## 核心设计方案

### 总原则

先落地技能底座，再接复杂技能，再补全长尾。不要继续在点击入口、战斗函数、旋转函数里散落 `switch`。

推荐新增或改造以下层次：

- `BoardActionResolver`：统一承接玩家动作、补牌、旋转、移动触发、二次移除、二次补牌、通关检查。
- `SkillRuntime` 或扩展后的 `SkillManager`：按事件名分发技能效果，例如 `onEnter`、`onMove`、`onMoveToSlot`、`onMoveEveryN`、`onCombat`、`onRemove`、`onMonsterPositionChangedBySkill`。
- `CardRuntime` 辅助函数：统一卡牌创建、原始属性、当前属性、移动计数、战斗计数、临时/持续修正、销毁前事件。
- `GridManager` 保留棋盘事实状态，但需要暴露原子操作：
  - `moveCard(from, to, reason)`
  - `swapSlots(a, b, reason)`
  - `rotateGrid({ reason, emitMoves })`
  - `removeCard(slot, reason, meta)`
  - `spawnCardToDeck(card, mode)`
  - `spawnCardToItemSlot(card)`

## 第一段：结算链与事件底座

目标：把“复杂技能能被正确触发”这件事打牢，不追求一次性补完所有技能。

建议范围：

- 为九宫格移动建立标准事件结果：每张移动卡记录 `{ card, fromSlot, toSlot, reason }`。
- 将三类现有入口统一接入结算链：
  - 点击怪物后怪物被移除
  - 点击帮助卡拾取
  - 点击相邻空格
- 拆开并统一：
  - `killMonster`：因伤害血量归零导致怪物死亡。
  - `removeCard`：任意卡离开当前区域。
- 建立输入锁生命周期：玩家动作开始锁定，移动触发与二次补牌结束后解锁。
- 保留现有视觉节奏，先不要大改 UI。
- 实现代表性技能来验证底座：
  - `散架`：被移除时生成骷髅头和无头骷髅到战斗卡组。
  - `不稳定`：每移动3次随机换位。
  - `不休追击`：移动到玩家正交相邻格自动战斗。
  - 一个“移动到格X”伤害技能，例如 `空中打击`。

验收标准：

- 三类玩家互动都走同一条“补牌 -> 旋转 -> 移动触发 -> 二次移除 -> 二次补牌 -> 通关检查”链。
- 自动战斗不会造成递归死循环或输入提前解锁。
- 直接技能移除也能触发 `removeCard` 相关效果和金币规则。
- `npm run build` 通过。

## 第二段：已接入牌组的复杂怪物技能

目标：优先补齐当前正式牌组里会实际出现的技能，不扩展备用牌组。

建议按类型分批：

- 移动计数类：
  - `丐帮同心`、`东西归我了！`、`吞石`、`发装备了！`、`丢石头`、`呼唤信徒`、`礼物`、`漫步`、`混合骨头`、`烈焰吐息`、`烈焰沸腾`、`异界帮助`。
- 棋盘操作类：
  - `不稳定`、`爱好旋转`、`乱步`、`快递`、`空间掌握`。
- 生成/移除类：
  - `献身`、`散架`、`折损散架`、`重新组合头`、`重新组合身`、`强力组合`、`暴力狂`、`暴力即养分`、`献祭`。
- 光环/条件类：
  - `痞气`、`学习成长`、`大聪明`、`兽人战术`、`石增长`、`石庇护`、`范围扩大`、`恋火`、`火之力`、`吸骨`。
- 自动战斗/强制战斗类：
  - `不休追击`、`和我打！`。
- 登场/战斗类从硬编码迁移到统一触发：
  - `给你一拳`、`转动`、`历战怪物`、`生存智慧`、`嗜血`、`尖盾/坚硬`、`先攻`。

验收标准：

- `07-数据/怪物卡数据.md` 中正式牌组的技能与代码数据一致。
- 怪物卡面攻击/护甲显示能实时反映持续光环和永久成长。
- 技能引起的位置变化能触发 `灼热观察`，系统旋转和帮助卡位移不触发。
- 技能引起的新空格能二次补牌，但不意外触发额外系统旋转。

## 第三段：帮助卡位置效果、遗物事件与验证工具

目标：把长尾交互和可验证性补齐，减少后续 AI 或人工修改时破坏结算链。

建议范围：

- 补全帮助卡在九宫格上的位置效果：
  - `滚石`、`治疗泉`、`瞭望塔`、`倍增塔`、`捕熊陷阱`、`烈焰`。
- 补全道具牌格中的持续效果：
  - `治疗泉` 战斗回血。
  - `瞭望塔` 道具格战斗随机伤害。
  - `倍增塔` 道具格双倍玩家目标帮助卡。
- 遗物事件从 `RelicManager.triggerEffects()` 的少量 switch 扩展为事件注册式。
- 增加开发验证工具：
  - 指定生成某只怪物到某格。
  - 快速触发一次旋转。
  - 打印最近一次结算链事件日志。
  - 显示卡牌移动计数和临时修正。
- 建立最小自动验证：
  - 构造纯数据单元测试或脚本级回放。
  - 至少覆盖移动计数、onRemove、自动战斗、二次补牌、光环刷新。

验收标准：

- 正式牌组和已实现帮助卡数据与权威文档一致。
- 一次复杂连锁中不会重复发金币、重复触发击杀、重复销毁容器。
- 通关判定只在战斗卡组为空且场上无怪物时发生。
- `npm run build` 通过，并通过浏览器手测关键场景。

## 重要风险与建议

- 最大风险不是某个技能公式，而是结算链分散。必须优先统一事件与移动结果。
- `removeCard` 和 `killMonster` 必须成为一等概念，否则“散架”“献身”“金币发放”“遗物击杀效果”会互相污染。
- 自动战斗必须加递归保护。推荐每轮结算有一个 action id 和最大链深，例如单次玩家动作内最多处理 32 个派生事件，超过则报警并停止。
- 技能造成的换位和系统旋转需要区分 `reason`，否则 `灼热观察` 会被误触发。
- 光环类不要直接永久改 `atk`。推荐保留基础值和修正源，显示与战斗时重算。
- 先做正式牌组，不做备用牌组。备用技能可保留数据结构扩展点，第三段以后再接。

## 待确认问题

1. `洗入战斗卡组` 是否必须随机插入/洗混，而不是放到牌堆顶？推荐按文档语义改为随机插入或洗混，除非某张卡明确写“置于牌堆顶”。
2. `不休追击` 这种移动触发的自动战斗若击杀怪物，是否只执行二次补牌、不再触发系统旋转？推荐按统一结算链处理：移动触发后的派生战斗不再额外旋转。
3. 本轮实现范围是否只覆盖正式牌组？推荐是，只把备用技能留到后续阶段。
